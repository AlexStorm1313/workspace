# Live delivery verification

Use when the user wants to verify Telegram delivery, not merely confirm successful schedule scans.

1. List jobs and identify the production target and any reusable verification job. Preserve the production job and dedupe state.
2. Use a separate script-only preview such as `$HERMES_HOME/scripts/bo3_live_delivery_check.py`. Acquire the production `watch.lock` while fetching to avoid concurrent operations against the shared named browser session. Fetch the live schedule, choose the earliest future non-live match with at least two filled stars, fetch its detail page, and apply exact detail metadata before rendering with production `format_alert`. Use the real current UTC countdown and real streams. Label the output as a delivery-test preview. Do not invoke `run_once`, write `sent.json`, or reuse an old snapshot as if it were live.
3. Reuse an existing one-shot job when possible; otherwise create a one-shot with `no_agent=true`, an explicit script, and the production Telegram target. Creating it paused prevents a race before preparation completes. After listing/discovering its ID, start a paused or completed one-shot with `hermes cron resume <job-id> --run-now`; direct `cron run` may refuse it while disabled.
4. Verify execution using `hermes cron runs <job-id> --limit 1`. A completed execution proves script completion, not delivery. Read the exact execution's durable delivery outcome before claiming the message was delivered.
5. If CLI output omits delivery fields, query the profile-local database read-only with Python `sqlite3.connect('file:' + str(home/'cron/executions.db') + '?mode=ro', uri=True)`. Inspect the schema before assuming column names. The tested query is `SELECT id, job_id, status, finished_at, delivery_outcome, error FROM executions WHERE id = ?`, binding the exact ID returned by run history. Require `status='completed'` and `delivery_outcome='delivered'`; otherwise report pending, failed, or unverified as recorded. Do not expose credentials or edit delivery records.
6. Confirm the production job remains active and that the preview did not mark the match as alerted. Report the delivery result and that normal alert eligibility remains unchanged; do not promise a future alert unconditionally because rescheduling, site availability, and scheduler uptime still apply.

When invoking the asynchronous cron tool's `run` action, consume its delivered completion event rather than polling. A foreground CLI verification flow can read records after the command or scheduler execution has finished.
