# BO3 match alerts

## When to Use

Maintain, verify, or change the installed BO3 starred CS2 Telegram watchdog. Do not use for unrelated esports sources.

## Prerequisites

Use the profile-local `$HERMES_HOME/scripts/bo3_watch.py` script-only watchdog and its `bo3_pipeline.py` and `bo3_alert_core.py` modules. Find existing jobs with `cronjob_manage(action='list')` and update rather than duplicate. The task preference is CS2, BO3 source `/matches/current`, at least two filled rating stars (any tournament tier; no S-tier-only restriction), details and direct stream links, with a default 10-minute warning and 1-minute checks. Confirm altered timing with the user's current request.

## Source rules

- Count `.o-icon--star-1.filled`, not all five star placeholders. Tournament tier is not rating.
- Read live pages via Hermes' configured `tools.browser_use_cli.browser_exec`; direct HTML and API HTTP requests can return 403. Use a dedicated named browser session and the supported helper entry point, not guessed endpoints or archived schedules.
- Wait for actual content, not just navigation completion. Detail readiness must include JSON-LD with `startDate`; a visible h1/tournament alone can precede metadata.
- Force browser timezone UTC. Schedule JSON-LD can contain only the first few rows, so join it to DOM match links and use displayed UTC time plus date from the match slug for remaining rows. Before alerting, retrieve exact `startDate` and tournament from the match page.
- Streams are buttons, not outgoing anchors. Click `.c-nav-streams__item`, read the actual `.c-widget-streams iframe` src, then convert Twitch channel, Kick player path, or YouTube embed ID to the genuine public stream URL. Do not infer providers from channel names. Capture languages and prefer English. If absent, say streams are not yet listed and include the match page.
- A successful schedule can legitimately contain zero matches. `bo3_pipeline.SCHEDULE_EMPTY_JS` proves this through the current-page table and Nuxt's actual `get-matches-csgo-matches-current` async request: hydration complete, status success, pending false, no request error, and the recognized metadata-only/empty live-response shape. Match rows must be absent, and block/challenge/HTTP-error states must be rejected. Read the app state through `#__nuxt.__vue_app__.$nuxt` (with the global-property fallback), unwrapping refs; do not treat an empty body/table or HTTP 200 alone as success. The observed empty payload is `[ [{paginationTag,meta,date}], {date,paginationTag,data:[]} ]`; unknown keys or nonempty nested match data fail closed. Schedule readiness accepts match rows OR this proof; the parser rechecks the proof before returning an empty list. Nonempty but unparseable rows remain a real error. Empty scans must be silent, write matched=0 health, and preserve sent history and result tracking. `test_bo3_empty_schedule` evaluates the real predicate in Node against empty/loading/error/blocked/populated fixtures and tests silent state preservation. Live source and reload tests must also accept a confirmed empty response rather than insist at least one match exists.
- Embed JavaScript selectors via Python `repr` where nesting quotes; test execution rather than trusting syntax checks alone.

## Scheduling and delivery

- Use `no_agent=true`, script filename relative to `$HERMES_HOME/scripts`, and an explicit `telegram:<chat_id>` resolved from the current profile's channel directory. Empty stdout must mean silence. This incurs no per-minute LLM usage.
- Preserve persistent dedupe under `$HERMES_HOME/data/bo3-match-alerts`; avoid overlapping scans with flock. Match URL identity, not start time, prevents reschedule duplicates.
- Gateway-managed Telegram delivery can work even when standalone `hermes send` fails for lack of a native token. Do not copy gateway secrets or invent credentials. Verify a one-shot no-agent delivery through the running gateway, then read cron execution history: `delivery_outcome=delivered` is stronger evidence than script completion alone.
- A durable enabled cron job still requires the host/gateway scheduler to run. Check `hermes cron status`, job health and `last_delivery_error` before claiming operational success.
- The user wants **one Telegram message per match**, including simultaneous starts. Production `bo3_watch.main` calls `run_once(..., alert_sink=bo3_delivery.queue_match)` and remains silent; do not reintroduce combined stdout delivery. `bo3_delivery.py` snapshots one match/streams to `data/bo3-match-alerts/outbox/<canonical-url-sha256-prefix>.json` and creates an immediate one-shot no-agent `bo3_alert_<hash>.py` job for explicit Telegram delivery. Each worker renders only its own snapshot at execution time, so countdown is current. Existing matching script job identity prevents duplicate queueing after an interrupted scan. Read back stored job before accepting enqueue. Queued workers add gateway-dispatch latency (typically another tick); do not promise an exact ten-minute warning.
- The watchdog marks persistent sent state after per-match queueing succeeds; queued jobs are durable before this point. Do not claim strict exactly-once delivery or clear existing sent history. Preserve already-queued snapshots and scripts until delivery is resolved.

## Browser recovery and diagnostics

Use `bo3_browser_recovery.py` through `bo3_pipeline.run_browser`, which embeds BROWSER_SUPPORT into the browser execution. Schedule/detail navigation calls `bo3_load(URL, READY)`; result batches call `bo3_load(url, READY, 15, 10)`. The normal loader waits up to 25 seconds for content, pauses two seconds after a failure, then reloads once with a 20-second readiness wait. Results use shorter per-page waits to fit their three-page batch. There are at most two navigation attempts, an 85-second shared browser-body deadline and a 110-second browser-tool timeout; do not add unbounded retries or override cron's execution cap. Driver startup/transport failure is not repaired by another page reload. `bo3_pipeline.run_browser` now inspects the latest BO3_DIAG event (including readiness/snapshot transport errors) plus the tool error; known driver/IPC timeout/disconnect patterns permit one fresh-controller retry, but explicit 403/429/challenge evidence and parser errors do not. `_restart_browser(session)` filters the installed native browser module's already-driven daemon identities by BOTH current `hermes_home_key()` and exact named session, then invokes its identity-checked `_reload_daemons` (`--reload`). Never stop every harness daemon, kill arbitrary PIDs, destroy cloud browser sessions, restart the gateway, or disturb another profile/session. This adapter uses inspected installed internals, so verify compatibility after Hermes upgrades; a missing/failed restart must remain visible, not silently become a successful empty scan. The fresh invocation shares the ORIGINAL 110-second outer budget and only starts with enough time left; never grant another full 110 seconds. Record `driver_restart_requested` and `driver_recovered` (the latter updates `last_recovery.json`), preserving the original failure. The source body only reads BO3; all alert enrollment/delivery remains outside the replayed browser execution. The next scheduled scan remains the outer recovery when budget is exhausted or a fresh controller still fails. `test_bo3_browser_recovery` covers bounded retry, denial/parser no-restart, remaining-time enforcement and profile/session scope. `test_bo3_browser_recovery_live` seeds a separate `bo3-controller-selftest`, deliberately injects ONE reported IPC timeout, then verifies the REAL controller PID changes and real BO3 content loads afterward; label this induced condition accurately, never as a natural outage.

Before reloading, capture HTTP navigation status where exposed, URL/title, DOM readiness, bounded page-text excerpt, match count, JS/promise/resource errors and failed/recent script/fetch resource statuses and timings. Install error listeners before navigation with Page.addScriptToEvaluateOnNewDocument; remove that registration after execution so named sessions do not accumulate hooks. Avoid cookies, headers and request/response bodies; strip resource URL query strings. HTTP status 0/unavailable is unknown, not proof of blocking. CAPTCHA/access-denied text is a possible indicator; main-document HTTP 403/429 or a visible challenge stops the retry rather than hammering or bypassing protection.

Browser code emits BO3_DIAG JSON markers; the host persists them locally to `data/bo3-match-alerts/diagnostics/events.jsonl`, with a roughly 1 MiB active log and one rotated backup, plus `last_failure.json` and `last_recovery.json`. Include session to distinguish pre-match and result collectors. Save the initial failure even when the reload succeeds. Diagnostics never appear as match alert stdout; a recovered scan remains successful and silent. Final exceptions point to the diagnostic file. Browser-tool failures without DOM access get a transport-error record instead of invented page evidence. Logs are created when an event occurs, not on every healthy scan.

Do not infer blocking from the horse placeholder title or missing match selectors alone. Successful neighboring scans and a fresh HTTP 200 do not identify the failed run's cause. Use the captured failure HTTP status, challenge indicators, script errors and resources. Generated schedule JS uses a raw Python string to preserve regex backslashes without SyntaxWarnings.

Run `test_bo3_browser_recovery` with the other unit suites. It covers timeout→reload→success, bounded total failure, no repeated requests on explicit 403/429, local failure/recovery persistence and transport errors. Run `test_bo3_browser_recovery_live` in Hermes' full Python environment for a real navigation/reload recovery test: it intentionally rejects the first navigation based on performance.navigation.type, requires actual match content after Page.reload, and redirects only its diagnostic writes to a temporary scratch home. This is an induced test condition, not evidence of a natural BO3 outage. Keep it in a separate named browser session and never send fake match notifications.

## Automatic failure maintenance

The user authorized proactive CS2 failure diagnosis and safe fixes, without asking about each raw cron warning. Keep healthy checks deterministic and script-only; wake an agent only for persistent/stale failures, with durable cooldowns. For installation, worker scope, staged test-before-deploy requirements, backups/rollback/recovery and verification, load [automatic maintenance](references/automatic-maintenance.md). Do not treat this authorization as permission to change alert eligibility, delete notification history, modify unrelated jobs/profiles, bypass access protection or alter credentials/models. Never claim an untested agent workflow or guaranteed repair of every outage.

## Results notifications

The user wants results only for matches that were eligible for the pre-match notification, not an unrelated feed of all finished 2+ star matches. Register eligibility before attempting pre-match delivery, so a delivery failure does not erase result tracking. Production `bo3_watch.main` supplies both `alert_sink=queue_match` and `result_tracker=bo3_results_watch.register_match` to `run_once`. Registration reuses `due_matches` with the exact detail-verified match snapshot; do not reapply a later potentially changed star rating. Preserve existing pre-match rules.

Run the separate `bo3_results_watch.py` no-agent job every five minutes. List jobs before updating; current name is `CS2 results for pre-match-eligible matches`. State lives in `data/bo3-match-results/tracked.json` under a short `tracking.lock`, with independent scan lock and `health.json`. No tracked/due matches means no browser/network call. Check at most three oldest-checked pending matches per run to fit cron's execution limit; rotate fairly. Pending/queued result state survives restarts; queue failures must keep tracking, while successful durable queueing stops further checks. Unresolved items older than three days stay visible as stalled with six-hour rechecks, not silently fabricated results or deletion.

`bo3_pipeline.collect_results(urls)` reuses the browser helper but uses named session/task `bo3-match-results` to avoid disturbing pre-match navigation. Read actual `.c-widget-match-status` content and `.c-nav-match-menu-item--game.c-nav-match-menu-item--finished` map scores. Readiness requires two widget team names plus JSON-LD startDate, NOT `.status`: live widgets can lack that element and instead have `c-widget-match-status--live` or Coming soon. Completed matches explicitly expose Ended. JSON-LD eventStatus can remain EventScheduled even when finished; endDate can be a date-only placeholder during live play. Never infer completion from endDate, score alone, disappearance from current listing, or a missing live marker. Normalize only an explicit terminal status and a complete plausible series score for the tracked BO format. Missing/naive end timestamps are omitted, not guessed. Finished map scores are optional and absence is explicit. BO3 can mark the series Ended while map rows still show 0–0 placeholders, and scores may fill asynchronously after the header is ready. `collect_results` gives map rows up to six additional seconds to settle, within the shared browser deadline. Never accept any numeric pair blindly: `bo3_results_core.map_score` rejects tied/0–0, sub-winning-total or too-close pairs, while preserving legitimate 13–0 shutouts. Consider only the played-map count implied by the final series score (ignore an unused decider), and reject map-winner totals that contradict that score. Keep invalid scores as null with their map names, not fabricated zeros. The renderer also validates old queued snapshots defensively and labels invalid scores **score unavailable**.

If some listed maps are incomplete, `bo3_results_watch` keeps the match tracking, stores `map_scores_pending_since`, the observed raw map rows and pending normalized result, and rechecks on the normal five-minute schedule. Allow about ten minutes from first detection before queueing the confirmed series result with unavailable labels for still-missing maps. Queue immediately if the map data becomes valid sooner; do not send a second copy or reset existing notification dedupe. When no map data is listed at all, retain the explicit no-map-data summary rather than inventing map names. Test the originally reported shape (1–2 series with final map 0–0), valid shutouts, contradictory map winners, delayed page hydration, repaired data and bounded-grace fallback. Already-delivered wrong messages are not automatically edited; provide a correction only from newly verified actual source data. Handle explicit cancelled/forfeit statuses without inventing a 0–0 or played maps; if the source does not expose usable status, keep pending/error visibility. Finished-list forfeits may be disabled buttons with no match URL, so never guess identity from them.

`bo3_delivery.queue_result` shares the snapshot, durable one-shot cron, formatting and read-back machinery with starts. Preserve the old URL-only identity for starting alerts; results use canonical URL plus a result discriminator and `bo3_result_<hash>.py`, preventing the start dedupe from suppressing results. Workers render `bo3_results_core.format_result`, one result per message with winner, series score, available map scores, tournament and BO3 link; no stream list. Old start snapshots without a notification_type remain compatible.

Do not backfill all historical finished matches on enable. Existing currently live matches can be enrolled only when a stored pre-match snapshot and actual sent timestamp prove eligibility; confirm still live from source. Subsequent enrollment is automatic through the eligibility hook. Historical finished matches may be used for parser tests/previews without queueing unsolicited result alerts.

Test with `python -m unittest -v test_bo3_alert_core test_bo3_watch test_bo3_delivery test_bo3_delivery_native test_bo3_results test_bo3_results_watch`. Verify live extraction on both ended and live matches, run both actual cron jobs, and read results health/state and stored schedules. Do not claim a result was delivered merely because the watcher succeeded; require the child result execution's delivery_outcome=delivered.

## Message layout

The user wants alerts without the scheduler's metadata header (job name/ID) or stop/manage footer. Use `hermes config set cron.wrap_response false` and verify with `hermes config get cron.wrap_response`. This is a profile-wide cron delivery setting, not part of the alert renderer; it applies to all cron jobs in this profile. The scheduler reads it at delivery time, so no gateway restart is needed.

Use the production `format_alert` renderer for both actual alerts and previews. The user prefers emoji-led sections, bold team/tournament names, a compact human countdown (for example `10m` or `5m 30s`, never fractional minutes), star emojis with bold BO format, an exact UTC timestamp, named clickable stream links with languages, and a named BO3 details link. Emit standard Markdown (`**bold**`, `[label](url)`); the Telegram adapter converts it to native entities/MarkdownV2. Do not emit raw HTML or pre-escape the whole message as MarkdownV2. Verify with the real Telegram adapter's `format_message` and a delivered real-match preview.

## Verification

- For a requested 1:1 test, use a real upcoming qualifying match from the live source and the production `format_alert` function, with real streams and the actual countdown. Send through the same cron delivery target without touching production dedupe. Do not substitute a settings-summary message or invent a ten-minute countdown.
- Re-arm a paused or completed one-shot verification job with `terminal(command="hermes cron resume <listed-job-id> --run-now")`. Plain resume can reject an old timestamp, and `cron run` can refuse a disabled job even when creation guidance suggests otherwise. Update its script if needed, then re-arm and verify a fresh execution's delivery outcome. Follow [live delivery verification](references/delivery-verification.md) for the tested preview and read-back procedure.
- Separate scan health, eligibility correctness, scheduling cadence, and delivery health when answering whether the job works. Read recent execution timestamps, `health.json`, and the actual `due_matches` predicate; a job label or health counter is not proof of the star threshold. Compare actual successive execution starts rather than equating `every 1m` with observed one-minute execution. Report any cadence discrepancy without changing timing unless requested.

For watchdog lock handling, the `with ...open(...) as lock` context releases the OS flock on close, including early return and exceptions. Never append a dangling `finally` or call nonexistent `lock.unlock()` on a file object. Cover the actual `main --inspect` path in tests as well as `run_once`, then verify a real cron run after edits.

Run core and watchdog tests with `python -m unittest -v test_bo3_alert_core test_bo3_watch test_bo3_delivery test_bo3_delivery_native` from `$HERMES_HOME/scripts`. The native test uses an isolated scratch HERMES_HOME to verify two actual distinct cron jobs and two separately rendered messages without sending fixture alerts to Telegram. Run the live integration test `test_bo3_pipeline.py` with Hermes' full Python environment; a bare host Python may lack dependencies. `bo3_watch.py --inspect` fetches the live schedule without sending or marking alerts. The ordinary watchdog emits eligible alerts, so do not run it manually during a due window merely to preview output. Read `data/bo3-match-alerts/health.json` and cron's durable run/delivery records after the first scheduled run.
